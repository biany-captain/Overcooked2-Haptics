# 0.6.2 严格个人反馈候选

历史方案：2026-11-27用户已将星级、真正拒单、订单超时和危险提醒改为本队共享，见[0.6.3方案](design-team-stars.md)。下文原始严格范围保留作历史；本人日常上菜/传菜/Combo的确认链路继续沿用。

2026-11-22，用户已明确选择：个人上菜、Combo及达星仅在能确认本人交付时输出；无法可靠归属的火灾/订单超时暂不自动反馈，保留功能、菜单试震与原波形。不得用团队回退增加震动次数。

## 真实证据与限制

0.6.1只读探针已在加入他人房间的客户端运行。保存日志中581笔订单结果均与交付台消息一一对应；其中183只交付盘子的先前持物释放记录属于本地厨师、398属于远端。另6条是没有盘子/订单结果的交付台拒绝。正常结果到盘子消息间隔中位0.8ms、样本最大35.6ms。见[evidence/runtime-personal-probe-0.6.1.txt](evidence/runtime-personal-probe-0.6.1.txt)。这些是关联候选，不是已验证的个人触觉输出；该轮没有明确上菜请求日志，也没有真实错误配方拒单覆盖。

只读IL检查确认当前游戏版本：PlaceHeldItem_Client发送Place请求，参数含具体厨师与目标组件；厨师持物移除、KitchenFlowMessage与PlateStationMessage提供后续应用状态。服务端在一次交付调用中先发送订单结果、再发送盘子消息，均走EntityEvent的可靠发送路径。此结论限当前安装版本及观察路径，不宣称其他平台/MOD/网络顺序均已验证。

## 个人确认链路

1. 捕获明确发出的本地Place请求：本人身份/Pad有效，当前持有盘子，目标确为交付台。普通台面/Take或更换目标使旧请求失效。
2. 必须观察到同一厨师对同一盘子的真实持物释放。盘子被任何厨师重新拿起或转手即使原请求失效，不能按“最后拿过它”猜上菜者。
3. 可信已应用的订单结果到达时，交付台必须仅有一项未完成结果，且仅有一只此前已释放的本地请求盘子符合队伍/目标。此时固定预期盘子，不能在随后收到盘子消息时重新猜。
4. 随后交付台确认必须包含这同一只盘子。订单结果决定成功、乱序、真正拒单、Combo或星级；交付台success单独不能证明正确上菜。全部吻合才交给原协调器与XInput绑定。

不固定等120ms或80ms；结果到齐立即排队。确认配对沿用既有180ms正常事件新鲜度上限，不延长旧上菜反馈。多项未完成结果、盘子冲突、反序/缺失/超时会让该台在当前关联周期静默；回合、暂停、失焦、菜单/停止、配置和绑定变化清理关联，不补播。严格失败关闭可能漏掉反馈，须从真实新日志讨论改进，不用扩大归属猜测掩盖问题。

Combo/比分/星级跟踪仍消费全部可信队伍进展，以保持真实等级和已达线状态；但远端/未知事件不输出，队友先达星也不会在随后本人普通交付时补庆祝。本人促成的同一次达星仍替代Combo/成功。未知危险/超时既不震动，也不打断庆祝音乐；这是本轮严格个人选择对旧全局危险优先方案的明确覆盖。

审查进一步证实：客机失败结果不携带台/订单/Combo/tip，且消息对象复用。快照归零这些残留字段，无归属拒单及其后续盘子确认静默消费，不隔离之后的新鲜有效成功。当前这类客机拒单也不自动打断音乐；原核心可归属负反馈的长低频与抢占契约、菜单试震均保留，不将模拟的有台身份拒单冒充实机可用路径。详见[审查裁决](review-personal-feedback.md)。

## 保留与验证

所有v1.6波形、Combo A、负反馈长低频、v1.7一二星无声/三星simple/四星cool、旧四星选项、BGM临时静音、F6/F10和现有开关/强度/音量保留。投掷、接住和已烧焦自动开关维持原值，不擅自开启。旧团队回退配置值保留，但严格个人运行时不使用它们。没有新菜单开关、音频/SDL依赖或每帧场景扫描。

新逻辑测试先缺API RED，再通过个人/远端、转手、错台、缺失与冲突、过期/重置、真正拒单和队友进展消费等用例。真实0.6.1片段缺少请求证据时应为零个人输出。软件通过不能替代新请求Hook与实机反馈验收。

安装候选后正常联机一局即可，不要求严格按顺序：观察本人上菜是否反馈、队友上菜是否静默；方便时将自己的盘子放台面让队友接手，检查不误归本人。记录未做步骤，不重测已稳定的整套音乐。错误配方、真实本人达星与房主/本地多人仍分别列待验证。

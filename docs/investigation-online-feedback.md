# 联机个人反馈排查 / 0.6.1校准版

2026-11-22。用户加入他人房间，本机一只手柄、一个厨师。用户报告菜单测试正常，实际联机震动很少；明确拒绝团队上菜反馈，要求个人反馈。

## 已证实的原因

保存日志中125次普通/乱序/未分类上菜、Combo及拒单被`delivery device not provable`过滤，11次获准自动反馈全部为达星（一星4次、二星4次、三星3次）。危险也因无法证明归属被过滤。投掷/接住按已确认的v1.6配置默认关闭，属于独立原因。见[evidence/runtime-online-0.6.txt](evidence/runtime-online-0.6.txt)。获准排程不等同独立观测到物理震动。

`PlayerResolver.FromTeam(requireSingleDevice:true)`调用`LocalOutputMap.IsSoleOutput`，同队存在远端厨师时返回false。现有消息缺少上菜者身份，原保护策略有意拒绝猜测；星级原本按本队比分处理，不走该唯一操作者路径，所以仍偶尔震动。不能把11次星级当成个人上菜识别成功，也不能用增加强度解决。

## 个人归属的数据候选

已只读检查当前安装的游戏程序集：KitchenFlowMessage包含队伍、交付台、比分/结果，没有直接厨师字段；ChefCarryMessage属于具体厨师的持物同步，包含物品实体；PlateStationMessage包含被交付的物品。交付台的success仅说明台面接收对象，不证明配方/订单正确，不能直接作为成功震动事件。

0.6.1只增加两处可选只读观察：厨师持物消息应用前/后，以及交付台消息应用后；现有比分探针增加交付台实例ID。使用原`Diagnostics.ScoreSourceProbe`开关，无新菜单、依赖、每帧扫描或游戏状态写入；探针自身异常明确记录并停用诊断，其余反馈继续。

日志记录客户端内厨师/盘子/交付台实例ID、本地标记、游戏Pad、持物前后变化与消息时间。只记录盘子相关持物变化，不记录玩家昵称/地址。**没有将这些观察转成反馈，不增加团队回退，不改变波形、去重、预算、Combo A或星级音乐。** 它是个人归属校准版，尚未修复个人联机反馈。全局达星/危险/超时在个人模式中的规则已向用户单独询问，未默改。

不能仅凭相近时间、最后持盘人或交付台success推定本人成功上菜。需要真实日志证实盘子→交付台→可信比分结果的关联和消息顺序；多人同台、转手、网络延迟、拒单等仍可能产生歧义，无法证明时保持静默。

## 用户手动对照

本轮不要以震动次数判断修复，反馈规则仍为原版，只采集归属证据。安装后手动重启、加入他人房间，建议普通允许上菜关卡：

1. 本人拿盘子上菜2次，接着让队友上菜2次；各次尽量间隔约2秒。
2. 本人拿盘子放在普通台面，再由队友拿走并上菜1次。
3. 可选：本人错误上菜1次；若方便，再与队友向同一交付台各上菜1次。
4. 正常退出，回复实际完成顺序。次数不同直接说明，不必重做全部星级/音乐测试。

随后先分析只读消息关联，再决定可靠个人路由；不要求房主先安装本MOD，也不自动控制游戏窗口。

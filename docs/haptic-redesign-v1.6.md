# Overcooked2-Haptics · 触觉重设计 v1.6（Combo A + 稀有失败长负反馈）

> **项目**：`Overcooked2-Haptics`；建议位置 `docs/haptic-redesign-v1.6.md`。  
> **状态**：用户已确认交互原则；具体毫秒数与马达速度为候选参数，**还未在游戏或实体手柄上验收**。  
> **对照**：在 v1.5 的基础上做增量修改，不得删除已可用的 1～4 星音乐庆祝、手柄映射与原有事件。  
> **用户确认**：Combo 方案 A——**只在明确升级到新的 Combo 档位时播放专属震动**，其余成功上菜只播放一次清脆短震；真正的失败/事故是低频长负反馈，稀有越严重越有分量；仍需避免噪音与持续震动。

## 1. 产品原则：让“少见的错误”有重量

《胡闹厨房2》拾取、切菜、投掷、交付非常高频；拒单、订单彻底超时、烧焦、起火通常比一般操作少。**重要性 × 发生频率 × 可挽回性**共同决定触觉表达：

- 成功：一次清脆干脆的“嗒”，立即归零；正向而不烦人。
- 乱序但成功：两声**轻低频**“咚、嗒”，指出断连击，但不能让玩家误以为菜被拒收。
- 真正拒单：一个**厚重且逐渐衰减**的低频“咚——”，总 430ms，明显区别于普通成功。
- 订单超时：两个较长且分开的低频重击，总约 505ms，表达“任务失败”，与拒单单次拖尾不同。
- 食物烧焦：**若存在已验证的独立烧焦事件**，总约 470ms 的明显低频拖尾；该事件在完成验证之前保持关闭。
- 起火：两段厚重震动并带拖尾，总约 820ms，事故最重。**只在进入起火状态触发一次**；持续起火的短提醒最长每 5 秒一次，并允许关闭，扑灭即停。
- 接近烧焦：中等力度的两段警告，不与已经烧焦/起火混为一谈；严格限频。
- Combo：高频节奏结构区分档位，只有 `×2/×3/×4` 等已确认**实际升级**才播，替代普通成功。
- 星级：沿用原先庆祝音乐 + 同步震动；同一次上菜星级奖励高于普通成功/Combo；危险能抢占庆祝。

> **注意**：毫秒数表示整个波形段总时长，包含静默；低频左马达并不表示能够指定频率，只是传统 XInput 的低频通道。不同 ERM、线性马达和驱动会造成截然不同的体感。

## 2. 核心事件波形 v1.6

`L/H` = XInput 左低频 / 右高频的归一化指令速度（0～1），播放器再乘总增益（初始 0.75）。表中为 **命令值，不是实测体感百分比**。完整数据见 `haptic_patterns_v1.6.json`。

| 事件 | 总时长 | 核心节奏 | 语义 | 触发方式 |
|---|---:|---|---|---|
| 成功上菜 | **90ms** | H0.72 / L0.02 一次短震 | 清脆、轻快 | 成功且无更重要反馈 |
| 乱序成功 | **315ms** | L0.29 125ms → 静默90ms → L0.17 100ms | 轻失误，不是拒单 | 必须验证曾有连击且本次有效交付打断 |
| 真正拒单 | **430ms** | L0.72 210ms → L0.47 95ms → L0.24 125ms | **沉闷、长拖尾** | 仅真正拒绝上菜 |
| Combo ×2 升级 | 235ms | H0.49 70ms → 静默70ms → H0.66 95ms | 双跳奖励 | 仅升级时 |
| Combo ×3 升级 | 375ms | 三次 H 脉冲，末音最长 | 三连奖励 | 仅升级时 |
| Combo ×4 升级 | 490ms | 三短一重，以 H 为主 | 高级连击 | 仅升级时；等级封顶后不重复 |
| 订单超时 | **505ms** | L0.61 190ms → 静默85ms → L0.55 230ms | 两下“失落感” | 超时事件发生 |
| 接近烧焦 | 450ms | L0.44 150ms → 静默120ms → L0.52 180ms | 危险临界提示 | 进入预警阈值，5秒限频 |
| 食物已经烧焦 | **470ms** | L0.66 230ms → L0.45 90ms → L0.23 150ms | 具体事故的沉闷拖尾 | **默认禁用，待 Hook 证实** |
| 起火 | **820ms** | L0.81 260ms → 静默90ms → L0.69 310ms → L0.30 160ms | 最重紧急负反馈 | 起火状态首次上升沿 |
| 起火持续提醒 | 470ms | 两次较轻低频脉冲，中间 130ms 静默 | 尚未扑灭，但不持续马达 | 每 5 秒最多一次；可关闭 |
| 投掷/接住/拾取/切菜 | 75～205ms或无 | 轻触为主 | 不干扰主体游戏 | **默认关闭普通投掷、接取、拾取/切菜**，玩家可开启 |

### 2.1 长负反馈不能等于一直开马达

- 较长的事件可以用**两段 + 静默**、**单次衰减**来表达；起火使用两段重击，拒单使用一整段渐弱，超时则是两次明确分开的拍点。
- 单个事件总时长上限建议 **950ms**，避免多事件长震串联；异常/暂停/切换游戏场景要立即输出 `0,0`。
- 严重事件可以抢占低优先级反馈，但不能每帧刷马达。火灾状态按 `scene + incident id` 去重。火焰灭掉立即取消持续提醒，不允许“补播”旧提醒。
- 如果玩家连续拒单，**不应无限排队**；按每手柄 10 秒负反馈有效振动时长约 2.2 秒的候选预算和失败事件 1200ms 冷却做合并/限流。特殊情况优先保留最新且最重要的状态。
- 起火比拒单优先，不让深沉失败震动遮盖正在发生的危机。

## 3. Combo 方案 A：已确定，不再做二次设计选择

Combo 跟踪器保留团队状态但**不能用“成功交付次数”替代游戏的真实 Combo 等级**：

1. 监听成功、拒单、失效事件（以现有项目中的真实客户端 Hook 为准）。
2. 同次交付 `deliveryId + teamId + levelEpoch` 的相关事件在约 80ms 的非阻塞窗口内合并：成功、`_wasCombo`、当前权威 Combo、星级门槛。
3. 只有**已验证的权威 Combo 档位** `newTier > oldTier`（首次确认进入该档）才发 `combo_x2_upgrade`、`x3`、`x4`。如游戏显示倍率与内部统计不同，需研究并写明映射证据。
4. 同档位连续正确上菜：只发 **delivery_success 的 90ms 清脆短震**。×4 以后继续正确上菜依然只是一次成功短震，不重复“×4 升级”。
5. 确定是乱序导致 Combo 断开：发**轻低频两段** `delivery_out_of_order`，但不发真正拒单震动。只有 `_wasCombo == false` 的情况下**证据不足以断言乱序**，例如首单、断连击后重建的第一单。
6. `OnFailedDelivery` 或等效**真正拒单事件**：发 `delivery_rejected`；不能混入一般 combo 中断或“顾客未给最高小费”的情况。
7. 若这一单达成星级，发星级震动，**不叠加普通成功/Combo**；如是非交付原因达成星级同样防重复。
8. 暂停、关卡重开、切换队伍、网络重连时重置去重和 Combo 状态。

**最终单一决策表：** 起火 / 紧急危险（可抢占） > 星级首次达标 > 真正拒单/订单超时 > Combo 升级 > 乱序成功 > 普通成功。一个交付只出现一个非危险反馈。避免把订单超时强行关联到另一个交付事件。

### 3.1 建议核心伪代码

```text
OnClientResult(evt):
    key = (sessionEpoch, teamId, evt.deliveryIdOrSafeCorrelation)
    bundle = aggregator.MergeWithin(key, 80ms) // non-blocking; thread-safe state
    if bundle.is_duplicate: return
    if bundle.star_milestone_verified: return EmitOnce(STAR_MILESTONE)
    if bundle.is_delivery_rejected:  return EmitOnce(DELIVERY_REJECTED)
    if not bundle.delivery_accepted: return
    if bundle.combo_tier_authoritative and bundle.tier > bundle.previous_tier:
        return EmitOnce(COMBO_UPGRADE[min(bundle.tier,4)])
    if bundle.verified_out_of_order_break:
        return EmitOnce(DELIVERY_OUT_OF_ORDER)
    return EmitOnce(DELIVERY_SUCCESS)
```

若本地客户端拿不到足够证据，优先安全降级为普通成功，而不是生成虚假的乱序/Combo 升级反馈。请保留事件日志，用于排查状态不同步。

## 4. 高低频马达与多手柄兼容

### 4.1 V1 默认 XInput

- **XInput 第一个**：Xbox 手柄、以 Xbox/XInput 模式运行的飞智黑武士 5 Pro、第三方 XInput 手柄；部分 PS 手柄能经 Steam Input/DS4Windows 暴露虚拟 Xbox 设备。
- `XINPUT_VIBRATION` 两路 16-bit 速度分别发送低频左马达与高频右马达。不是精确频率波形；**不承诺任意手柄会有相同体感**。用户启动时可以分别测试左右马达、最短有效震动和阈值。
- 避免假定游戏玩家 1 == XInput 槽位 0；支持手柄认领与显式映射。无法识别具体上菜者时，不得默认向所有手柄广播个人操作震动。
- 控制器 API 线程或独立调度器输出非阻塞脉冲，Hook 仅入队。所有异常、场景关闭、插件卸载、设备断连都要执行安全归零。

### 4.2 V2 可选 SDL3

- `SDL_RumbleGamepad(gamepad, low_frequency_rumble, high_frequency_rumble, duration_ms)` 支持标准双通道震动与时长。运行时还需维护 SDL 事件及设备生命周期。
- 可能与 XInput / Steam Input 虚拟手柄重复枚举：必须建立**物理设备只绑定一个输出后端**的映射机制。不能靠同名简单去重，无法确认映射时提供手动指定选项。
- 新增后端是**可选模块**，不强制安装驱动、不默认替换游戏 DLL、不将已稳定 XInput 路径打坏。

### 4.3 Steam Input

- 普通第三方手柄若已经映射为 XInput，则复用 XInput 后端，避免再额外通过 Steam Input 或 SDL 震同一设备。
- 若准备直接使用 Steam Input API，要先确认当前游戏进程是否有可用实例、InputHandle 和 API 初始化条件，**不能假定 BepInEx 插件可以直接使用任意 Steam Input Handle**。
- 不同设备左右马达的感觉可能相反/缺失。提供 `per_motor_gain`、`pulse_duration_scale`、`min_pulse_ms` 的校准方案；物理上只有单马达的设备依靠**节奏而非“高低频”**维持成功/失败区别。

### 4.4 推荐配置面板

- `成功反馈`、`乱序提醒`、`拒单负反馈`、`订单超时`、`火警`、`Combo升级` 独立开关。
- `总强度`、`低频增益`、`高频增益`、`负反馈时长倍率（候选 0.8～1.25）`。
- “静音/均衡长负反馈/戏剧化负反馈”预设，但更改这些参数**不能改变**事件分类含义。
- 每个玩家本地手柄拥有自己的校准值，且每个设备仅一个后端控制。

## 5. 防噪音和优先级

**只给重要事件震动；长负反馈既稀有又受限。** 默认拾取、连续切菜、行走、普通投掷、接住全部不震。玩家想增强动作手感可自行开启。建议独立的预算：普通 ≤1.2s/10s、负反馈 ≤2.2s/10s、紧急 ≤2.5s/10s（均为每个手柄实际有效马达工作时长；均是测试候选，不是医学限值）。

- **同一事件替代**：Combo 升级 / 星级代替成功，乱序代替成功，拒单没有成功反馈。
- **不同事件抢占**：起火即时终止正在播放的成功/Combo/星级马达震动；星级音频是否淡出另按声音策略管理。
- **不排队叠加**：旧的普通交付/动作事件超过 180ms 未播放即丢弃；长负反馈不会排队持续播放到下一次操作。
- **紧急例外**：火警首次触发可越过普通预算，但必须有硬上限。持续火灾提醒必须独立冷却、可关闭、退出/扑灭即停。
- **合并 80ms 非阻塞**：允许权威 Combo 值和星级状态稍后才到；若实际实测感觉延迟，需降低窗口或优化 Hook，不能以延长震动掩盖延迟。
- **调度安全**：XInput 没有“自动持续时间”，需要主动归零；不得在 Unity `Update` 高频同步阻塞、不得 Hook 中 `Sleep`、不得多个线程抢写相同槽位。

## 6. 实现次序（逐步改现有工程，不重做）

1. **审计现有源码**：列出已存在的 Hook、事件模型、ComboTracker、HapticEngine、音效与设备后端；找出真正存在重叠震动的路径，记录证据。
2. **建立可测试的波形模型**：读取 v1.6 JSON，校验 0..1、步长、总时长、冷却和未知事件；FakeBackend 脱离游戏运行。
3. **先改三种交付事件**：普通成功单次 H、乱序成功两段 L、真实拒单更长单段衰减 L；在 log 中记录 delivery/order/team/authority，确保分类准确。
4. **实现 Combo A**：只在已证实等级提升时播专属一条；其余连续成功归为普通成功。对首单、断连击恢复和 ×4 以后增加测试。
5. **改订单超时与危险状态**：区分 approaching-burn / burned / fire-start / active-fire；仅真实起火上升沿强震，扑灭就取消持续提醒；暂不可证实的烧焦事件不要虚构。
6. **补全调度器**：80ms 合并、优先级抢占、每手柄冷却、过时丢弃、预算、归零生命周期与可关设置。
7. **完成手柄校准**：XInput 样机验证、非 XInput 后端作为独立后续模块；飞智/Xbox/虚拟 Xbox 多设备去重和玩家映射需记录实测。
8. **自测+交付**：单元测试→Windows 线下手柄测试→游戏真实 Hook 测试；更新 `docs/test-report.md`、`docs/hook-research.md`、`CHANGELOG.md`；附已测设备/模式和未测清单。

## 7. 最低验收场景

| 场景 | 期望结果 |
|---|---|
| 首单顺序成功 | 一次 90ms 高频成功，**不误判 Combo 升级** |
| 同档位继续正确上菜 | 只播一次成功，绝无 Combo 叠加 |
| 连击第一次升至 ×2/×3/×4 | 各播放自己的高频节奏，**不播成功短震** |
| 已到 ×4 后继续正确上菜 | 普通成功，**不重复 ×4** |
| 成功但乱序并经权威状态验证 | 两段较轻低频，不使用拒单长震 |
| Combo 恢复的第一单 / 无权威等级 | 不凭 `_wasCombo=false` 误判乱序或升级 |
| 真正拒单 | 430ms 低频拖尾，且只发一次 |
| 一次订单超时 | 505ms 分离的两段低频，与拒单可盲辨 |
| 食物临界烧焦 | 450ms 两段警告，进出阈值不重复震动 |
| 真正食物烧焦 | 仅独立 Hook 验证后启用低频 470ms |
| 起火与 Combo 同时发生 | 起火的 820ms 占主导，旧 Combo 不延后补播 |
| 火仍持续 / 已扑灭 | 最多 5 秒一次提醒 / 扑灭立即结束提醒 |
| 暂停、失焦、卸载、断开设备 | `Stop(0,0)`，马达不残留 |
| 本地双人不同手柄交付 | 仅准确关联的个人手柄反馈；未知不广播 |
| 游戏里与 Steam Input / SDL 同时存在 | 单设备只有一个有效输出后端 |
| 15 分钟持续游玩 | 无连续震动噪音；成功/乱序/失败/Combo 可明显辨认 |

**主观验收建议**：在实际设备上随机进行 20 组盲测：`成功 / 乱序 / 真拒单 / Combo×2` 识别率 ≥85%，拒单对成功的误判不超过 1 次；每个手柄记录使用 15 分钟后是否出现“吵、麻、累”的反馈。门槛只是项目目标，并非客观通用标准。

## 8. 明确的事实与待确认界限

- 公开资料有候选游戏方法：`ClientKitchenFlowControllerBase.OnSuccessfulDelivery`（带 `_wasCombo` 等参数）、`OnFailedDelivery`、`OnOrderExpired`；**签名和服务端/客户端角色必须结合当前游戏版本确认**。
- `_wasCombo` 不足以告诉你具体升级到 ×2/×3/×4，需要联动团队状态；实际 Combo 值/显示倍率对应关系必须先调试。
- XInput 两路电机指令不等于精确 Hz/力度；线性马达、高阶 DualSense、飞智专有触觉另做可选适配，不在当前“普适方案”里虚假承诺。
- Meta 的触觉指南认可低频/沉闷、节奏/间隔和稀有高重要性事件更明显，但同时反对持续和无界震动。因此**用有限的较长负反馈，而不是不限时强震**。
